**总体策略**
- 建议把 `Subagent` 做成“父代理编排、子代理执行、结果回收”的模型，不要一开始就做成多个可随意写盘的自治代理。
- 这个仓库最适合的路线是：先做“串行、受控、只回传结果”的 `MVP`，再逐步放开到“可产出 patch”，最后再考虑并行化。
- 第一原则：`父代理` 保留审批权、完成权和最终交付权；`子代理` 只负责局部分析或局部实施。
- 第二原则：`taskSessionId` 可以共享，`runId` 和 `agentContext` 必须隔离；否则现有完成门禁、预算控制、审批恢复会被污染。
- 第三原则：一开始不要让子代理直接 `applyPatch`、`writeFile`、`runCommand`，先让它返回“计划 / 证据 / patch 草案”。

**先定边界**

- 工具注册仍以 [agentModes.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentModes.ts)、[agentToolRegistry.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentToolRegistry.ts) 为中心，先新增“委派工具”而不是重写所有工具。

**阶段 0：方案冻结与契约设计**
- 目标：先把 `Subagent` 的职责边界写清楚，避免后面进入“子代理既能规划又能审批又能写盘”的失控状态。
- 核心决策：
  1. `父代理` 负责整体目标、任务拆分、审批沟通、最终完成。
  2. `子代理` 负责局部子任务，例如“只分析路由影响”“只修改某一组件树”“只整理测试失败原因”。
  3. 子代理结果统一分为三类：`analysis`、`proposed_patch`、`execution_report`。
  4. 子代理默认不能直接结束整个任务，不能改父代理状态机。
- 需要落地的契约：
  - 子任务身份：`subagentId`、`parentRunId`、`delegationId`
  - 子任务范围：目标描述、允许文件范围、允许工具范围、预算
  - 子任务产物：摘要、证据、候选补丁、建议验证命令、风险说明
- 涉及文件：
  - [agentToolTypes.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentToolTypes.ts)
  - [types.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/types.ts)
  - [prompts.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/prompts.ts)
- 阶段验收：
  - 形成稳定的数据模型和行为边界文档
  - 明确“哪些动作只能父代理做”

**阶段 1：数据模型与可观测性打底**
- 目标：先把“父子关系”和“运行证据”记下来，让系统能看见 Subagent，而不是先追求能力。
- 重点改动：
  - 在运行时上下文里增加父子运行关系字段，位置优先从 [agentToolTypes.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentToolTypes.ts) 和 [types.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/types.ts) 统一扩展。
  - 在任务会话中记录“谁委派了谁、子任务状态、产物摘要、失败原因、预算消耗”。
  - 在步骤流中增加新的 step 类型，例如“创建子代理”“子代理开始”“子代理完成”“子代理失败”“子代理结果已回收”。这部分会影响 [routeAgentSteps.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/routeAgentSteps.ts)。
  - 指标侧增加父子运行维度，避免现在的运行指标把子代理当成普通工具调用。涉及 [runMetrics.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/observability/runMetrics.ts) 和 [taskMetrics.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/observability/taskMetrics.ts)。
- 这一阶段不要做的事：
  - 不做并行
  - 不做子代理写盘
  - 不做子代理审批
- 阶段验收：
  - 一次父代理运行中能清楚看到子代理树
  - 任务历史能回放子代理生命周期
  - 指标能区分父代理失败还是子代理失败

**阶段 2：串行只读 Subagent MVP**
- 目标：先做最安全的版本，证明“拆任务”这件事本身是有效的。
- 推荐能力范围：
  - 子代理只允许只读工具和分析工具
  - 子代理输出分析结论、候选文件、影响范围、修改建议
  - 父代理基于结果决定是否自己生成 patch
- 最适合先开放给子代理的工具：
  - 代码搜索、文件读取、定义提取、影响分析、存在性检查、相似模式检索
  - 对应核心在 [agentTools.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentTools.ts)
- 运行方式建议：
  - 父代理通过一个新的委派工具触发子代理
  - 子代理复用现有 `agentRuntime`，但以受限 registry 启动
  - 子代理拿到独立预算，不能吃掉父代理全部步数
- 提示词层建议：
  - 在 [prompts.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/prompts.ts) 中给子代理单独的 system prompt
  - 明确告诉子代理：“你不是最终交付者，你只负责在限定范围内收集证据并给出可执行建议”
- 这一阶段的收益：
  - 可以把“先摸清影响范围”“先找类似实现”“先看失败原因”从主循环拆出去
  - 能明显降低父代理上下文污染
- 阶段验收：
  - 父代理可把“分析某个模块”委派给子代理
  - 子代理返回结构化结果，并被父代理引用
  - 完整任务仍只由父代理交付

**阶段 3：可产出 Patch 的实施型 Subagent**
- 目标：让子代理不仅会分析，还能在局部范围内产出 `proposed_patch`，但仍不直接写入工作区。
- 为什么这一步要单独做：
  - 这是能力提升最大的阶段，但也最容易和现有安全模型冲突
  - 当前系统以“先产 patch，再审阅，再应用”为核心，子代理必须适配这个模型
- 设计建议：
  - 子代理允许使用 `proposePatch` 一类工具，但默认禁止 `applyPatch`
  - 子代理产出的 patch 先回收到父代理，由父代理统一合并、裁剪、排序、去冲突
  - 父代理最终向前端只暴露一份可审阅补丁集，而不是多份散乱 patch
- 重点改造点：
  - [agentModes.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentModes.ts)：新增“子代理模式”或“受限 Act 配置”
  - [agentPatchTools.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentPatchTools.ts)：支持标记 patch 来源为某个子代理
  - [patchStore.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/patchStore.ts)：支持 patch 与 `delegationId / subagentId` 关联
  - [agentRuntime.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentRuntime.ts)：增加“父代理回收子代理 patch 并二次判断”的流程
- 冲突处理建议：
  - 第一版不做自动三方合并
  - 如果两个子代理改同一文件，直接回退成“父代理手动整合”
  - 同一文件的多个 patch 只允许有一个进入最终候选集
- 阶段验收：
  - 子代理能稳定生成局部 patch
  - 父代理能识别 patch 来源并整合
  - 不破坏现有 diff 审阅和 checkpoint 流程

**阶段 4：审批、恢复与完成门禁联动**
- 目标：把 Subagent 接入现有最强的可靠性链路，否则它只是“会跑”，但不能“上线”。
- 需要重点联动的模块：
  - [agentPermissions.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentPermissions.ts)
  - [agentCompletionPolicy.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentCompletionPolicy.ts)
  - [taskSessionStore.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/taskSessionStore.ts)
  - [progressRecovery.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/progressRecovery.ts)
- 审批策略建议：
  - 子代理产生的高风险动作不直接弹审批
  - 由父代理统一汇总并发起审批请求
  - 这样用户只面对一个主会话，不会出现“多个子代理同时请求批准”的混乱体验
- 完成门禁建议：
  - 子代理不能直接调用任务级 `completeTask`
  - 子代理完成只代表“子任务完成”
  - 父代理在汇总子任务后，才进入现有的完成证据判断
- 恢复策略建议：
  - 如果父代理在等待审批时中断，恢复后要能知道哪些子代理结果已回收、哪些未回收
  - 如果子代理失败，父代理可选择重试、降级自己处理或改派其他范围
- 阶段验收：
  - 审批恢复后不会丢失父子运行关系
  - 完成门禁仍能准确阻止“没有真实改动却宣布完成”
  - 子代理失败不会把整条任务历史打坏

**阶段 5：预算隔离与上下文治理**
- 目标：避免 Subagent 上线后把现有 `context budget` 体系搞乱。
- 当前仓库在预算控制上很强，这一层必须保住：
  - [agentBudgetPolicy.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentBudgetPolicy.ts)
  - `contextBudget` 目录下各模块
  - [agentTools.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentTools.ts) 中的读取额度与 artifact 恢复机制
- 具体策略：
  - 父代理和每个子代理都有独立步数预算
  - 子代理默认拿小预算，例如只够完成一个局部目标
  - 子代理结果回收给父代理时，优先回传摘要和引用，不直接回传大块原始内容
  - 超大工具结果继续走 artifact 引用恢复机制，不把子代理全量输出直接塞回父代理 prompt
- 推荐规则：
  - 父代理负责“宏观决策”，子代理负责“局部证据”
  - 父代理不继承子代理的全部 `filesRead/searchQueries`，只继承最终有价值的结构化结论
  - 子代理预算打满后，父代理必须收到可诊断的失败原因，而不是一个空结果
- 阶段验收：
  - 大任务拆分后总 token 使用更稳定
  - 父代理上下文噪音下降
  - 子代理失败不会导致父代理直接失控重试

**阶段 6：并行化能力**
- 目标：在串行 Subagent 稳定后，再做真正的性能提升。
- 不建议过早做并行的原因：
  - 会立即放大 patch 冲突、审批顺序、日志排序、指标归因、上下文一致性问题
  - 当前系统的很多可靠性设计是按单主循环思路构建的
- 并行化建议分两步：
  - 第一步：只并行“只读分析型”子代理
  - 第二步：再并行“产出 patch 型”子代理
- 并行调度要解决的问题：
  - 最大并发数
  - 同目录/同文件冲突预检
  - 父代理等待策略，是全部收齐还是先到先用
  - 子代理取消传播，父代理终止时要能取消所有子代理
- 需要重点关注：
  - [agentRuntime.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/agentRuntime.ts)
  - [taskSessionStore.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/taskSessionStore.ts)
  - [runMetrics.ts](file:///c:/Users/wplicn/Documents/web-ide/apps/server/src/observability/runMetrics.ts)
- 阶段验收：
  - 并行分析型子代理不会互相污染结果
  - 用户在 UI 上能读懂并行步骤的来源和状态
  - 任务取消、超时、失败归因都正确

**阶段 7：UI 与任务体验补全**
- 目标：让用户“看得懂” Subagent，不然功能再强也难以信任。
- 建议 UI 展示：
  - 父代理步骤下可折叠显示子代理运行
  - 子代理显示：目标、范围、状态、耗时、关键结论、是否产出 patch
  - patch 审阅中显示“来源子代理”
  - 任务历史中显示父子运行树
- 交互建议：
  - 用户默认只和父代理沟通
  - 不让子代理直接向用户提问，子代理的问题回流给父代理整合
  - 出错时父代理用自然语言总结，而不是把多个子代理原样日志都甩给用户
- 阶段验收：
  - 用户能从活动流理解“为什么要委派”
  - 用户能看出每个 patch 来源
  - 出问题时能定位到具体子代理

**测试计划建议**
- 单元测试优先覆盖：
  - 父子运行关系持久化
  - 子代理工具白名单
  - 子代理预算隔离
  - patch 来源关联
  - 完成门禁不被子代理绕过
- 集成测试优先覆盖：
  - 父代理委派只读子代理分析某模块
  - 父代理委派实施型子代理产出 patch
  - 子代理失败后父代理降级继续
  - 审批恢复后继续回收子代理结果
- 验收测试优先覆盖：
  - 一个大任务被拆成两个子任务并成功交付
  - 两个子代理尝试改同一文件时被正确阻止或回退
  - 并行只读子代理不会触发错误完成
